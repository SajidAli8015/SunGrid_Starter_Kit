# Notes: shortcuts and limitations

One line per item: what, and why.

- Only Azure OpenAI is tested end to end; the OpenAI, Anthropic and Gemini clients are written against their SDKs and covered only by offline construction tests.
- `complete_json` uses prompt instructions plus Pydantic validation, not provider structured-output features, because those differ across providers and Azure API versions.
- `complete(temperature=None)` falls back to `llm.temperature` from config, so the YAML value is actually used (small deviation from the brief's `temperature=0.0` default).
- `complete_json` returns a `JSONResponse` (value plus raw responses), not the bare model, so token counts and latency are available for the per-query log.
- Only `LLM_PROVIDER` overrides YAML from the environment for now; other settings are YAML-only until there is a need.
- Any exception from a provider SDK is wrapped in `LLMError` (broad catch, secrets redacted, cause chained) so callers handle one error type.
- The fake provider built by the factory returns `{"status": "ok"}` by default so `check-llm` can run offline; tests script their own responses.
- The Anthropic client does not send `temperature`: the installed `anthropic` 1.x SDK no longer accepts it on `messages.create`, so determinism there is not controlled.
- Doc categories for docs 07-14 are our assumption (the kit labels only 01-05, and 06 as ambiguous); only doc 06 has a secondary category, pending evaluation results.
- Manifest `owner` values other than the Incentive Program committee and the Billing team (the only teams the KB names) are plausible placeholders.
- Chunk size uses an approximate token count (words plus punctuation), not the embedding model's tokenizer; good enough for a ~350-token limit, and no current section comes close.
- Oversize sections are split on paragraph, then bullet, boundaries; a single oversize table or paragraph is kept whole rather than cut mid-row/mid-sentence.
- `secondary` is stored in Chroma as a comma-joined string plus one `cat_<category>` boolean per category, because Chroma metadata cannot filter on lists.
- Ingestion always drops and rebuilds the whole collection (14 small docs); no incremental updates, even though `content_hash` would allow them.
- fastembed caches the downloaded model in its default temp-dir cache; a cleaned temp dir means a re-download on the next run.
- `search` uses fastembed's `query_embed`/`passage_embed` as-is; no BGE query instruction prefix or score threshold tuning yet.
- The classifier's confidence is self-reported by the LLM and uncalibrated. It only ever widens search (low confidence -> unfiltered), except in the guarded `non_relevant` exit, which also needs weak unfiltered retrieval.
- The classifier prompt names the Rooftop Rebate Program (for `needs_eligibility_check`) and the fault-code rule refers to "the category whose description covers fault codes" rather than naming a category, so all category text still comes from `config/categories.yaml`.
- The fake LLM's dict keys match the system prompt as well as the last message; tests key on full query strings to avoid accidental matches.
- The margin fallback compares top-1 scores only: when a wrong category's own chunk is the unfiltered top-1 (margin 0), the filter is kept and the right doc can drop out (dev set: 3/80 wrong-label cases at margin 0.05).
- Unfiltered top-1 scores for in-scope and out-of-scope dev queries overlap: general-solar, other-utility and prompt-injection queries score like terse in-scope ones ("E07" 0.635). The score ceiling alone cannot decline safely; the classifier label carries most of that decision.
- The dev set (28 queries) is small and written by us, so thresholds tuned on it are rough; the held-out evaluation set is the honest check.
- The calibration "best ceiling" breaks ties toward the lowest value, because wrongly declining an in-scope question is worse than answering an out-of-scope one (grounding can still abstain).
- Azure's content filter rejects the prompt-injection dev query (d23) with HTTP 400 before the model sees it; the classifier raises `LLMError`. Calibration records it as an error (counted as a miss), and the answer pipeline must treat a classifier failure safely (no answer from guesswork). Errors are not cached, so that call is retried on every calibration run.
- `fallback_margin` set to 0.04 from calibration: wrong-label robustness 78/80 (vs 77/80 at 0.05), and the fallback never fires when the label is right (0/20) at any margin from 0.02 to 0.10; 0.04 is the largest margin with the best count.
- `non_relevant_score_ceiling` kept at 0.60, not the suggested 0.63: "E07" scores 0.635, so 0.63 leaves 0.005 of headroom, and wrongly refusing an in-scope question is the worst outcome. A missed decline (general-solar and other-utility queries at 0.627) is harmless because the answer step abstains when the chunks do not support an answer.
- Multi-doc questions can lose one source to the filter: the lapsed-certification dev query is labelled program_policies (0.90), margin 0.015 keeps the filter, so the rebate doc (unfiltered rank 2) drops out of the top 5. The deciding fact is in the installer certification doc (rank 1), so the answer can still be grounded. Tags left unchanged on purpose.
- `LLMContentFilterError` is mapped for Azure only (HTTP 400 with code `content_filter`, matched by attributes). OpenAI, Anthropic and Gemini signal blocked input differently (or not as an exception) and are not mapped; their rejections stay generic `LLMError`.
- The eligibility service is called once per check with a timeout and no retries: a retry could double-call a real (possibly non-idempotent) service, and a failure escalates to a human anyway. A timed-out call keeps running in its worker thread (Python cannot kill it); its result is discarded.
- A known non-household tier short-circuits before missing slots are asked for: there is no point collecting income or ZIP for a rebate the tier cannot get, and the case is flagged for a human.
- The gate also rejects an ineligible result whose `reason` is empty or contains a money amount (TOOL_ERROR), because the reason is shown to the member verbatim and must not carry a figure.
- The adapter returns problem codes (`not_a_zip`, `not_finite`, ...) and never the raw value; the member-facing wording for fields, problems and tiers lives in `config/messages.yaml`.
- Slot extraction caches results in git-ignored `.cache/extract/`; those files hold slot values (ZIP, income) the member typed. Acceptable for a local prototype; a deployed system would not persist them.
- Slot extraction tells the LLM which slots were already asked for, so a bare follow-up such as "yes" can fill the one question it unambiguously answers; values are still only taken when stated.
- The guard's money pattern catches `$500`, `USD 500`, `500 dollars` and a bare `$`; amounts written out in words ("five hundred dollars") are not caught.
- LLM calls per message (gpt-4o, 12 demo messages): knowledge answer 2 (classifier + answerer); eligibility decision 3 (classifier + extractor + next-steps answerer), or 2 when the slots arrive as a reply to a pending question (no re-classification); clarifying question or non-household tier 2; out-of-scope decline 1; average 2.2. Tokens ~1.9k in / 130 out for a knowledge answer, ~2.4k / 180 for a decision.
- Latency (same 12 messages, median): knowledge 8.2 s, eligibility decision 19.3 s, clarifying question 9.8 s, decline 3.2 s. Classification varied from 2.2 s to 17 s (eligibility questions were consistently slow); possibly SDK retries on throttling (`llm.max_retries: 2`), not confirmed because retries are not logged. Calls are sequential; no streaming.
- Known answer failure (demo 5, "Can a Community-tier member run for the board?"): the composer answered "No" and claimed only Household-tier members can vote, contradicting the cited Voting Eligibility section. The KB is genuinely incomplete there (the policies doc defers board eligibility to the governance doc, which never states it), so the right answer was "not stated" plus review. Prompt rule 4 was not enough; not tuned on the demo. Candidate fixes for the eval phase: a claim-by-claim verification pass, or a stricter "if a cited chunk does not literally state it, say it is not stated" rule.
- Demo 4 ("What is the income threshold?") abstains and escalates instead of saying the threshold is published annually by the Board. Safe, but less helpful than possible.
- Next-steps queries are a list per verdict with merged hits: one combined "documents + funding" question left the Documentation Requirements section outside the top 8, and the composer then paraphrased eligibility rules as "documents" (a quiet grounding failure the guard cannot catch, since it only checks amounts).
- The next-steps composer's `needs_human_review` is not propagated: an ineligible reply naturally mentions the appeal route, and escalating every ineligible member on that basis would flood reviewers. Escalation follows the eligibility outcome.
- `TrackedLLM`/`UsageTracker` are request-scoped but not thread-safe; the CLI handles one message at a time. A server would need one tracker per request.
- The agent runs with LLM caches off (they store member text); every `ask` message makes real calls. Tuning commands (`classify`, `calibrate`, `extract-slots`) keep their caches.
- `escalation_notice` appends the composer's own `review_reason` to member-facing text; it is short LLM text, not a fixed string.
- Eval `category_ok` uses the last classified category of a conversation, because a slot-filling reply to a pending eligibility question is not re-classified (q18's final turn).
- Eval treats `service_unavailable` (provider failure) as an `error` for the question, separate from a wrong answer; errored questions cannot pass and do not stop the run.
- Eval workers build their agents one at a time: concurrent Chroma client setup raced ("Could not connect to tenant default_tenant") in an offline smoke run, which made one worker's questions fail. Queries still run in parallel.
- Eval counts in `summary.md` come from repeat 1; `--repeat N` adds a stability section rather than averaging.
- Full-context baseline scores only the text checks (contains, not-contains, hard gate) and skips eligibility and non_relevant questions; latency there is the composer call only.
- The p95 latency in eval summaries uses the nearest-rank method; with 20 questions it is close to the maximum.
- Baseline eval (run 20261020T155131Z, commit 3228bbc, untuned): auto_pass 18/20, no errors. q02 (board seat) repeats the demo-5 failure: it asserts candidates must be Household-tier (not in the KB) and is not escalated. q13 abstains although both Annual Impact Report chunks were retrieved, apparently because "now" is not the report's fiscal-year end. Neither was fixed in this task (baseline only).
- `scripts/clean_clone_check.py` has been run on Windows only (PASS: install, 279 tests, ingest with a fresh model download, search, check-llm with the fake provider). One attempt failed inside pip's own temp-folder bookkeeping (`pip-build-tracker` missing) and passed on re-run; macOS/Linux paths are written but not exercised.
- F2 (review of 6619e93): the session keeps its last eligibility verdict; after INELIGIBLE or TIER_NOT_HOUSEHOLD a knowledge answer containing a `$`-style amount is dropped (abstain, escalated as `amount_after_non_eligible_verdict`). It uses the same money pattern as the guard, so worded amounts still pass; an ELIGIBLE_PRELIMINARY verdict, or a new session, lifts the check.
- F1 (review of 6619e93): the extractor's `installer_approved` now uses the clarifying question's test (on the approved list at the time of installation, the working electrician's certification current); a lapse during the install is false, hedges or non-SunGrid certifications are null. A plain "the installer is SunGrid-approved" with no lapse mentioned still counts as true, otherwise nearly every free-text eligibility question would need an extra turn. The rule is prompt-only (no keyword override in code) and not yet checked against the live model. Dev query d29 (lapse during install) was added; the thresholds and `calibration.json` still come from the 28-query run.
- F4 (review of 6619e93): in a non-eligible reply, the LLM-written part is also checked for amounts without a currency sign (digit groups such as 4,000 or 4000, and numbers next to k, cents or watt). It fails safe: a year or a 3-digit percentage in the next-steps text drops that text and only the deterministic reply is sent. Amounts in words are still not caught. The deterministic part is checked for `$` only; the test covers every reason the stub can return.
- F6 (review of 6619e93): `CopilotAgent.handle` ends with a catch-all. Any non-LLM failure returns `temporarily_unavailable` as outcome `service_unavailable`, escalated with code `internal_error` and the exception type only, and is still logged. Reusing that outcome means eval counts it as an error. A blank message gets the fixed `empty_message` text (outcome `empty_message`, not escalated, no LLM call, logged); pending eligibility state is kept.
